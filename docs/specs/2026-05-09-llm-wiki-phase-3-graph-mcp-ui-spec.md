# LLM Wiki Phase 3: Graph, MCP, And Read-Only UI Spec
**Date:** 2026-05-09
**Last Updated:** 2026-05-09
**Author:** Codex with Akshay Jain
**Status:** Proposed - clarifications incorporated, pending implementation plan

---

## Problem Statement

Phase 2 makes `llm-wiki` more useful for multi-project retrieval and manual write-back, but the workspace is still not a human-friendly or agent-native knowledge graph.

Current gaps:

- no true backlink-oriented graph
- no entity extraction or entity resolution
- no automatic cross-link proposal queue
- no MCP server for Claude Code/Codex native querying
- no browser UI for inspecting the current wiki, graph health, backlinks, and proposed edits

The user wants a first Phase 3 slice that is useful and safe: **read-only graph and MCP surfaces first, proposed edits queue for cross-links, and UI as a distinct implementation slice**.

---

## Goal

Add a deterministic graph layer, read-only MCP server, proposed cross-link edit queue, and separately planned Python-served UI so humans and coding agents can inspect the wiki as a connected knowledge system without allowing automation to mutate durable markdown by default.

---

## Product Boundary

### In Scope

- deterministic graph rebuild from durable wiki markdown
- backlink and entity graph stored in existing `state/index.db`
- high-confidence proposed cross-link edits inside wiki pages only
- CLI commands for graph rebuild, summary, backlinks, and proposal listing
- read-only MCP server plus proposed-edit listing
- UI design and implementation slice for a Python-served local browser
- separate verification plan for graph core, MCP contracts, and UI
- database schema expansion and migration/rebuild behavior
- audit logs for graph rebuilds and proposal generation

### Explicitly Out Of Scope For First Phase 3 Slice

- automatic markdown rewrite during graph rebuild
- MCP approval or mutation tools
- AI-first entity extraction
- raw snapshot cross-link insertion
- public hosted web app
- auth/multi-user collaboration
- open-ended autonomous wiki maintainer
- replacing Phase 2 deterministic query runtime
- fixing all Phase 2 retrieval/embedding limitations

### Deferred But Designed For

- optional AI entity enrichment
- approval/apply flow for link proposals
- concept hub/entity page generation
- richer UI with graph editing and review workflows
- Streamable HTTP MCP transport
- Graph export to Cytoscape/Obsidian-compatible formats

## Clarifications Incorporated

- UI should be a distinct implementation slice, not bundled into the first graph/MCP core implementation.
- Frontend should be Python-served local UI, not a separate React/Vite app in the first pass.
- Graph tables should be added to the existing `state/index.db`.
- Entity extraction should be deterministic first, optional AI enrichment later.
- Proposed edits should be limited to high-confidence missing links inside wiki pages.
- MCP should expose read-only tools plus proposed-edit listing only.
- `uipro init --ai codex` was run and the UI/UX Pro Max skill was used to inform the frontend design and verification guidance.

## Current Implementation Realities

### Session-Memory Learning

When a workflow tool creates only an empty session shell, that is not useful memory capture. A session artifact needs a real dossier: source session metadata, actions taken, linked tasks, observed defects, and carry-forward fixes. Otherwise the output is only a container, not a knowledge asset.

The interface should stay source-agnostic: `import-session --session-id <id>` should work for both Codex and Claude Code sessions, and `close-session` should be the generic way to finalize and summarize the captured session.


The Phase 3 design must account for the current Phase 2 implementation:

- `state_db.py` is the schema source of truth and uses idempotent `CREATE TABLE IF NOT EXISTS`.
- `state/index.db` is derived state and should remain rebuildable.
- `rebuild-retrieval` populates `chunks` and `fts_chunks`, but `projects`, `wiki_pages`, `snapshots`, and `snapshot_files` are not fully backfilled yet.
- query synthesis remains deterministic/project-card based, despite the Phase 2 spec describing richer hybrid retrieval and OpenAI synthesis.
- `query_evidence.chunk_id` currently stores citation strings rather than real chunk IDs.
- embeddings are not generated by default, so `health` may report `missing embedding rows` after successful lexical indexing.
- `writeback.py` can approve pending DB rows, but query does not yet create proposals automatically.

Phase 3 must build stable service functions over actual workspace artifacts and graph tables rather than depending on incomplete Phase 2 metadata population.

## User Motivation And Satisfaction Criteria

The user wants the wiki to feel more like a compounding knowledge system and less like isolated project cards.

Satisfaction signals:

- can ask an agent to inspect wiki context through MCP without copy/paste
- can open a local UI and see projects, entities, backlinks, and proposed links
- can rebuild graph state repeatedly with deterministic results
- proposed cross-links are useful enough to review rather than noisy
- no markdown files are changed unless explicitly approved in a later workflow

Friction to avoid:

- noisy entity extraction
- graph views that are visually impressive but not useful
- UI requiring a separate Node app before value is proven
- MCP tools that can mutate durable wiki state too early
- proposed edits that drift after manual file edits

## Functional Requirements

### FR1: Graph Rebuild

- Add `llm-wiki rebuild-graph --workspace <path>`.
- The command must parse durable wiki markdown and rebuild graph tables in `state/index.db`.
- Rebuild must be deterministic for the same workspace state.
- Rebuild must not mutate markdown files.
- Rebuild must clear and repopulate graph-derived tables in one logical operation.
- Rebuild must log counts, skipped files, unresolved links, and proposal counts.

### FR2: Page Graph

- Represent wiki pages as graph nodes.
- Include durable pages:
  - `wiki/projects/**/project-card.md`
  - `wiki/projects/**/overview.md`
  - `wiki/projects/**/decisions.md`
  - `wiki/reports/*.md`
- Exclude logs, generated indexes, raw snapshots, `.DS_Store`, caches, and non-wiki files from first-slice graph extraction.
- Preserve stable page IDs based on workspace-relative path.

### FR3: Entity Extraction

- Extract entities deterministically from:
  - project slug
  - project name
  - aliases from project card metadata
  - durable page title
  - headings
  - existing internal links
  - exact known project/entity names mentioned in prose
- Normalize entity names via lowercasing, punctuation stripping, whitespace collapsing, and slugification.
- Avoid broad low-confidence noun phrase extraction in first slice.
- Store extraction source and confidence rationale.

### FR4: Entity Resolution

- Resolve entities by:
  - canonical slug match
  - alias match
  - exact normalized title/name match
- If multiple candidates match, mark as ambiguous and do not create a high-confidence link proposal.
- Store alias-to-entity mapping in `entity_aliases`.

### FR5: Backlinks And Edges

- Create typed graph edges for:
  - `links_to`
  - `mentions`
  - `backlinks_to`
  - `belongs_to_project`
  - `alias_of`
  - `derived_from`
- Materialize backlinks from graph edges rather than scanning markdown on each query.
- Preserve source path and optional line/character span when available.

### FR6: Proposed Cross-Link Edits

- Generate link proposals only for high-confidence entity mentions in durable wiki pages.
- Proposal generation must skip:
  - existing markdown links
  - code fences and inline code
  - frontmatter
  - citations
  - URLs
  - raw snapshots
  - logs
  - generated indexes
- Each proposal must include:
  - proposal ID
  - source path
  - target node/entity ID
  - original text
  - replacement markdown link
  - start/end span or line
  - base content hash
  - confidence score
  - rationale
  - status
  - created timestamp
- First slice lists proposals only; approval/apply is deferred.

### FR7: CLI Graph Read Surface

Add commands:

- `llm-wiki graph-summary --workspace <path> [--project <slug>]`
- `llm-wiki backlinks --workspace <path> --target <page-or-entity>`
- `llm-wiki proposed-links --workspace <path> [--status pending]`

CLI output may be human-readable by default, but service functions must return structured data for MCP/UI reuse.

### FR8: MCP Server

Add a read-only MCP server command:

- `llm-wiki mcp --workspace <path>`

Default transport:

- stdio for local Claude Code/Codex integration.

Expose tools:

- `search_wiki(query, project_slugs?)`
- `get_page(path_or_id)`
- `get_entity(entity_id_or_name)`
- `list_backlinks(page_or_entity)`
- `list_proposed_edits(status?)`
- `get_graph_summary(project_slug?)`

MCP must not approve proposals, write files, mutate DB state except read-only connection setup, or run rebuild automatically unless explicitly added as a future operator tool.

### FR9: MCP Resources

Expose read-only resources where useful:

- `wiki://page/{page_id}`
- `wiki://entity/{entity_id}`
- `wiki://project/{slug}`
- `wiki://graph/summary`

Resources must be safe to read repeatedly and must not depend on live network access.

### FR10: Local UI Slice

UI is separate from graph/MCP implementation but must be specified now.

Add later command:

- `llm-wiki serve --workspace <path> [--host 127.0.0.1] [--port <port>]`

UI must:

- read from `state/index.db` and markdown pages
- avoid markdown mutation
- show graph summary, search, pages, entities, backlinks, and proposed links
- expose graph visualization plus accessible list/table fallback
- bind to localhost by default

### FR11: Health And Lint Extensions

Extend `health` or add graph-specific health checks for:

- missing graph tables
- stale graph rebuild relative to wiki file hashes
- unresolved internal links
- duplicate entity aliases
- ambiguous entity resolutions
- proposed edits with stale base hashes
- graph nodes without source pages where a source is required

### FR12: Audit Logs

- Append human-readable graph rebuild logs to `logs/graph-log.md`.
- Persist structured rebuild runs in `graph_rebuild_runs`.
- Include:
  - timestamp
  - workspace path
  - graph schema version
  - pages parsed
  - nodes/edges/entities created
  - proposals created
  - warnings/errors

## Non-Functional Requirements

### NFR1: Safety

- No markdown mutation during rebuild, MCP reads, or UI reads.
- Proposed edits must be inert records until a future approval flow.
- All paths must be workspace-relative and validated to stay inside workspace.

### NFR2: Determinism

- Rebuilding graph twice from identical workspace content must produce the same stable sorted graph snapshot.
- IDs, aliases, edge types, and proposals must be deterministic apart from timestamps/run IDs.

### NFR3: Trust And Explainability

- Entity and link proposals must include rationale and evidence.
- Ambiguous matches must be visible, not silently resolved.
- UI and CLI must clearly distinguish existing links from proposed links.

### NFR4: Local-First Operation

- Graph rebuild, MCP server, and UI must work without network access.
- Optional AI enrichment must remain disabled by default and out of first-slice implementation.

### NFR5: Performance

- Rebuild should handle the current durable workspace in under 30 seconds on a local developer laptop.
- UI graph view must not try to render the full graph when it exceeds configured node/edge limits.
- MCP responses should support result limits and deterministic ordering.

### NFR6: Accessibility

- UI must support keyboard navigation, visible focus states, skip links, readable contrast, and reduced-motion preferences.
- Graph visualization must always be paired with an adjacency list/table fallback.

### NFR7: Maintainability

- Graph extraction, graph repository, proposal generation, MCP adapters, and UI routes must be separate modules.
- CLI must remain thin and delegate to services.
- Tests must cover services directly rather than only CLI output.

## Architecture

### Recommended Shape

```text
wiki markdown
  -> graph extractor
  -> graph repository
  -> state/index.db graph tables
  -> CLI graph commands
  -> MCP read-only server
  -> later Python-served UI
```

### Backend Modules

- `src/llm_wiki/graph_models.py`: dataclasses or Pydantic-style structures for nodes, edges, entities, aliases, proposals.
- `src/llm_wiki/graph_schema.py`: graph SQL statements and schema helpers.
- `src/llm_wiki/markdown_graph.py`: deterministic markdown parsing and span detection.
- `src/llm_wiki/entity_resolution.py`: normalization, alias matching, ambiguity handling.
- `src/llm_wiki/graph_builder.py`: rebuild orchestration.
- `src/llm_wiki/graph_repo.py`: SQLite read/write queries for graph state.
- `src/llm_wiki/link_proposals.py`: high-confidence missing-link proposal generation.
- `src/llm_wiki/mcp_server.py`: FastMCP server and tool/resource adapters.
- `src/llm_wiki/web_app.py`: later Starlette app factory for UI.
- `src/llm_wiki/web_static/`: later static JS/CSS assets.
- `src/llm_wiki/web_templates/`: later Jinja templates.

### Technology Choices

- SQLite remains the derived state store.
- `markdown-it-py` is recommended for deterministic markdown token parsing.
- `mcp[cli]` / FastMCP is recommended for MCP server implementation.
- Starlette + Jinja2 + Uvicorn is recommended for the local UI slice.
- Cytoscape.js is recommended for graph visualization only if paired with an accessible table/list fallback.
- NetworkX may be used for in-memory graph algorithms/export later, not as persistence.

### MCP Tool Contracts

All MCP tools return structured JSON-compatible payloads and are read-only.

`search_wiki(query: str, project_slugs: list[str] | None = None, limit: int = 10)`

- Searches page titles, entity aliases, and lexical chunks where available.
- Returns stable IDs and snippets.

`get_page(path_or_id: str)`

- Returns page metadata and markdown content.
- Rejects paths outside workspace.

`get_entity(entity_id_or_name: str)`

- Resolves canonical entity and returns aliases, pages, backlinks, and outbound edges.

`list_backlinks(page_or_entity: str, limit: int = 50)`

- Returns backlinks from graph edges.

`list_proposed_edits(status: str = "pending", limit: int = 50)`

- Returns proposals only; does not apply them.

`get_graph_summary(project_slug: str | None = None)`

- Returns counts and last rebuild metadata.

## Frontend Design

### Product Shape

The UI is a local read-only workspace browser. It should make current wiki knowledge easier to inspect, not become a content management system in first slice.

### Visual Direction

Use the UI/UX Pro Max skill as input, adapted to a clean technical dashboard:

- Fira Sans for body
- Fira Code for technical IDs and metadata
- slate/ink neutral palette
- restrained blue/green accents for actions and health
- no emoji icons; use SVG icons only
- high contrast and clear focus states
- reduced motion support
- graph visualization paired with list/table fallback

### Layout

- Header: workspace name, graph health, last rebuild, search
- Left nav: Overview, Projects, Pages, Entities, Reports, Proposed Links, Health
- Main content: selected page/entity/proposal/graph neighborhood
- Right context panel: backlinks, outbound links, related entities, citations, proposed links

### Core Components

- `WorkspaceShell`

- `GraphSummaryCards`

- `PageList`
- `PagePreview`

Keep browser state minimal:

- URL route and query params are the primary state.

- `/`

## User Journeys

### Journey 1: First-Time Graph Rebuild

1. Operator runs `llm-wiki rebuild-graph --workspace <path>`.
2. CLI prints summary and warnings.
3. Operator runs `llm-wiki graph-summary --workspace <path>`.
4. Operator sees counts and pending proposals.

Success: operator trusts that graph state was built without touching markdown.

### Journey 2: Agent Queries Wiki Through MCP

1. Operator configures Claude Code/Codex to run `llm-wiki mcp --workspace <path>`.
2. Agent calls `get_graph_summary`.
3. Agent calls `search_wiki` and `get_entity`.
4. Agent uses returned citations/paths in its answer.

Success: agent retrieves wiki context without scraping files manually.

### Journey 3: Human Reviews Proposed Links In CLI

1. Operator runs `llm-wiki proposed-links --workspace <path>`.
2. CLI lists proposal IDs, source path, target, confidence, and rationale.
3. Operator manually inspects the source file or waits for future UI approval flow.

Success: proposed links are visible and reviewable without automatic edits.

### Journey 4: Human Browses UI

1. Operator runs `llm-wiki serve --workspace <path>`.
2. Browser opens local dashboard.
3. Operator searches an entity, sees backlinks and related pages.
4. Operator checks proposed links queue.

Success: the current wiki is understandable without memorizing CLI commands.

## Edge Cases

- Missing `state/index.db`: graph commands should tell the user to run `rebuild-graph`; UI shows first-time empty state.
- Stale DB after markdown edits: health flags stale graph based on content hashes.
- Ambiguous entity alias: no high-confidence link proposal; record warning.
- Existing markdown link: do not propose duplicate link.
- Mention inside code block/inline code/frontmatter: skip.
- Mention inside citation or URL: skip.
- Target page deleted after proposal creation: proposal becomes stale/superseded.
- Manual file edit after proposal creation: base hash mismatch marks proposal stale.
- Cyclic graph edges: allowed; UI must handle cycles.
- Very large graph: UI loads neighborhood, not full graph by default.
- Unicode and punctuation aliases: normalize carefully, preserve original text.
- Duplicate project slugs: lint/health should flag; graph builder should avoid unsafe resolution.
- Path traversal attempts through MCP/UI: reject any path outside workspace.
- MCP stdout pollution: server must never print non-MCP logs to stdout in stdio mode.

## Risks And Mitigations

| Risk | Impact | Mitigation |
|---|---:|---|
| Entity noise | High | deterministic extraction only, high confidence threshold, ambiguity warnings |
| Unsafe proposed links | High | skip code/frontmatter/URLs/existing links, require base hash |
| Patch drift | High | base content hash on every proposal |
| MCP accidental mutation | High | read-only tools only, tests assert no file/status changes |
| Local HTTP exposure | Medium | bind UI to `127.0.0.1`, origin validation if HTTP MCP added |
| Graph UI overload | Medium | neighborhood loading and table fallback |
| Spec outruns Phase 2 reality | Medium | build graph from markdown and actual DB tables, not promised-but-unfilled metadata |
| Accessibility regression | Medium | keyboard/focus/reduced-motion tests and adjacency list |
| Dependency creep | Medium | keep UI Starlette/static JS first, defer React/Vite |

## Decision Log

| Decision | Options Considered | Choice | Rationale |
|---|---|---|---|
| Graph state location | existing `state/index.db`, separate `graph.db`, markdown-only graph files | existing `state/index.db` | simplest derived state, shared health/CLI/MCP access |
| First extraction approach | deterministic, OpenAI-first, hybrid | deterministic first | predictable, cheap, testable, avoids noisy graph |
| Proposed edit scope | wiki pages only, all markdown, wiki+raw | high-confidence wiki pages only | protects immutable raw/log/index artifacts and reduces churn |
| MCP scope | read-only + proposal listing, mutation tools, search-only | read-only + proposal listing | useful for agents without allowing durable mutation |
| MCP transport | stdio, Streamable HTTP, both first | stdio first | local clients support stdio; avoids HTTP origin/auth complexity |
| UI stack | Python-served, static generated site, React/Vite | Python-served local UI | fits CLI-first package and keeps UI as separate slice |
| UI graph library | Cytoscape.js, D3 custom, no graph visual | Cytoscape.js later with table fallback | strong graph interaction, but accessibility requires non-visual alternative |
| Markdown parser | regex-only, `markdown-it-py`, tree-sitter markdown | `markdown-it-py` | deterministic token parsing with less correctness risk than ad hoc regex |
| Approval flow | first-slice apply, list-only, autonomous rewrite | list-only first | validates proposal quality before write mutations |
| AI enrichment | required, optional later, never | optional later | preserves local deterministic graph while leaving extension path |

## Recommendations Adopted From Research

- Use FastMCP / `mcp[cli]` for Python MCP implementation because the official Python SDK supports tools, resources, structured outputs, and stdio/HTTP transports.
- Use stdio as the default MCP transport because the MCP transport spec defines stdio and Streamable HTTP, and says clients should support stdio where possible.
- Do not write any logs to stdout in MCP stdio mode; stdout must contain only MCP messages.
- Use Starlette/Jinja/static files for the first Python-served UI because it is lightweight and supports templates/static assets cleanly.
- Use Cytoscape.js only for visualization, not as the only way to inspect graph data; always provide an adjacency list/table.
- Use MCP Inspector for MCP contract verification.
